2. Sahin Mehbub Sarkar — application track, detailed task list (sequential)

Spec = the prototype. Referenced by file name. Definition of Done per task: reviewed + merged, lint/typecheck/tests green (platform/scripts/), deployed to staging, demo-able.

Week 1 — Foundation

D1.1 Auth core: JWT + OTP + RBAC SAHIN M.
  • Access + rotating refresh JWT (reuse detection); OTP via email/SMS for registration + login.
  • RBAC middleware: roles student|teacher|admin; permission decorators on routers; audit log table for admin mutations.
  • Rule from prototype: staff assign exam track; students cannot self-override.
Accept: register→OTP→login→role-scoped /me; refresh rotation tested; admin action writes audit row.
D1.2 Core schema v1 SAHIN M.
  • Alembic migrations: users, students, staff, enquiries, cms_documents, cms_revisions, media_assets, audit_log.
  • Domain enums from prototype: exam tracks (ielts-a, ielts-g, toefl, pte, duolingo, cambridge, oet, general) and IELTS part ids (l1–l4, r1–r3, rgt, w1, w2, s1–s3, gv, strategy) — mirror PARTS/TRACK_PARTS in bloom-data-library.js/bloom-tracks.js.
  • pgvector enabled; kb_chunks reserved for Raja's AI track.
Accept: alembic upgrade head clean from empty DB; seed script creates demo data.
D1.3 Design system port + app shells SAHIN M.
  • Port bloom-core.css/bloom-site.css tokens → TS theme; shared primitives (sidebar layout, cards, tables, forms, modal, toast).
  • Shells per role: public layout, authed portal layout (sidebar + router), admin layout.
Accept: primitives demo page renders; all three shells route correctly.
D1.4 Freeze API contracts JOINT
  • With Raja: OpenAPI for platform↔AI (POST /ai/chat streamed; GET /ai/profile/{student_id} = track, CEFR, weak modules, error history), platform↔WAISE (template send, inbound webhook, enquiry alert), mail provisioning (check_username / create_mailbox / suspend / reset / quota).
  • Contracts committed + versioned in platform/contracts/; stubs generated so both sides code independently.
Accept: contracts merged; mock servers available for both sides.

3. Raja Sahin track A — DevOps, hosting & mail (what, when)

S1 (W1) Environments + CI/CD RAJA·OPS
  • App VPS (≥8GB, 16GB recommended): Docker stack (Postgres+pgvector, PgBouncer, Redis, api, web), nginx reverse proxy, TLS, staging.* subdomain.
  • CI: PR → ruff+mypy+pytest (api/ai-tutor), eslint+tsc+vitest (web), docker build; auto-deploy to staging on merge to main.
  • Daily pg_dump backups + uptime probe from day one.
Accept: merge → live on staging; backup restores verified once.
S2 (W3–W6) Mail server — dedicated VPS RAJA·OPS
  • Dedicated mail VPS (isolated from app VPS): Postfix + Dovecot + Rspamd + SOGo, dockerised (mailcow-style); mailbox DB + per-mailbox quota.
  • DNS: MX, SPF, DKIM, DMARC, PTR/rDNS · IP warm-up starts W3 — deliverability needs weeks of lead time.
  • Provisioning API (per W1 contract): check_username / create_mailbox / suspend / reset / set_quota — token auth + IP allowlist; live by W6.
  • Deliverability monitoring + rate limits; mail-tester score ≥9/10.
Accept: mailbox created via API → usable in SOGo/IMAP in seconds; SPF/DKIM/DMARC pass.
S3 (W4) Production cutover — website RAJA·OPS
  • Prod VPS, bloomielts.com domain + TLS, CDN, brotli, uptime probe → website live for Month-1 demo.
S4 (W11–W12) Hardening + go-live RAJA·OPS
  • Load test with Sahin M.: hundreds of simultaneous timed mock attempts; PgBouncer/Redis tuning.
  • Security pass (RBAC audit, rate limits, dependency scan); backup restore drill; monitoring + alert routing.
  • Production cutover runbook; ops + handover docs for academy staff.
Accept: load report meets target; restore drill done; platform live on prod.

4. Raja Sahin track B — Bloom AI Tutor engine (horizontally scalable)

Concept: independent deployment, own scaling group. Capacity = number of stateless workers behind the Redis queue — add workers, add capacity. AI down ≠ platform down.

A1 (W1–W4) Skeleton + knowledge base RAJA·AI
  • ai-tutor/: FastAPI gateway (auth, rate limits, SSE streaming) → Redis queue → stateless Python worker pool.
  • LangGraph agent graph: profile node (student context from Postgres) → retrieval node (pgvector) → LLM node (streamed).
  • Ingestion: Bloom curriculum → chunking → embeddings → pgvector kb_chunks; re-indexable.
Accept: chat request → retrieved-context streamed answer; KB re-index job runs.
A2 (W5–W8) Quality + personalisation + guardrails RAJA·AI
  • RAG quality pass on Bloom material; agent profiles per module (Listening tutor ≠ Writing tutor); guardrails + escalation to a human teacher for off-scope questions.
  • Student-profile context node live (track, CEFR, weak modules, error history); curated eval set + regression harness before any model update.
Accept: eval set green; answers cite Bloom KB; student context measurably changes responses.
A3 (W9–W12) Harden + integrate + meter RAJA·AI
  • Harden /ai/chat (rate limits, streaming, fallbacks); per-student usage metering (~₹30–80/student/mo target); single-worker prod deploy (Essentials scope — multi-worker load test + scale-out runbook = post-launch phase).
  • Hand the frozen /ai/chat to Sahin M. for the portal chat UI; isolated production deployment.
Accept: tutor live in portal under expected launch load; metering report exists.

5. Handoffs & hard dependencies

  • W1 contracts (D1.4) gate everything cross-side: AI, WAISE, mail — freeze in Week 1, no exceptions.
  • Mail: Raja's provisioning API (S2, by W6) → gates Sahin M.'s admin mailbox controls (D3.4) and student registration (D5.1, W10). IP warm-up cannot be compressed — start W3.
  • AI: Raja's /ai/chat (A3, by W11) → gates Sahin M.'s chat UI (D5.6, W12). Sahin M. builds against the W1 contract stub, never waits for the real service.
  • Exam engine: teacher exam builder (D4.2, W9) publishes into the same engine the student mocks use (D5.3, W11) — same codebase, same tables.
  • Environments: Raja keeps staging/prod ahead of the build; Sahin M. should never be blocked waiting for a server — escalate same-day if that ever happens.

Risk watchlist

  • Single-dev bandwidth — the whole app on one pair of hands; W10–12 is the densest stretch. Weekly demos catch slippage early; scope changes never absorbed silently.
  • Mail deliverability — new IP/domain lands in spam without warm-up; that's why DNS auth + warm-up start W3, not later.
  • Content dependency — AI tutor and library need curriculum; escalate if the Week-4 bulk handover slips.
  • Exam-day load — mock engine load-tested in W11 before go-live, not discovered in production.
